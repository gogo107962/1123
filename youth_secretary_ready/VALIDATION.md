# 구현·검증 결과

작업 기간: 2026-11-15~17 (한국 시간). 서비스 검증: 2026-11-17. 단계별 최종 코드와 검증 범위는 아래 v0.8 기록을 참고한다.

## 결과

기존 FastAPI + SQLite + Vanilla JS 프로젝트를 유지하여 **가상 정책 데이터 입력 → 자격·방향성 중복 제한 판별 → 조건별 서류 준비 → 로컬 LLM의 도구 선택·실행 → 사용자 승인 → DB 저장·복원** 흐름을 검증했다. 전체 실제 정책을 검수하거나 운영 서비스를 완성했다는 뜻은 아니다.

시간은 이 PC에서 세션 생성 등 준비 API 요청을 포함해 측정한 두 사례다. 평균 성능·모든 입력의 정확도·응답 시간 보장을 의미하지 않는다. 시험 환경은 Windows, Python 3.13.7, 메모리 약 32GB, RTX 3050 4GB Laptop GPU, Ollama 0.40.16, qwen3:4b였다.

최종 pytest에는 Starlette의 httpx TestClient 사용 중단 예정 경고 1건이 있다. 실패는 없으며 검증된 의존성 조합을 `requirements-lock.txt`에 기록했다. 현재 프로덕션 코드 변경 없이 해당 경고를 숨기지 않았다.

## 수정한 동작

- 정책 조건의 연산자와 값 타입을 함께 검증한다. 미표현 조건은 `manual_checks`로 남겨 확인 필요로 처리한다.
- 대체서류 조건이 미확인인 경우 기본 서류를 확정하지 않는다. 여러 대체 조건이 동시에 참이면 임의로 첫 항목을 고르지 않는다.
- 서류 보유는 자기 신고로 취급하며 원문 조건 확인 작업을 유지한다.
- `/api/preview`의 토큰으로 사용자가 본 조건을 고정한다. `/api/confirm`은 현재 조건·정책·날짜와 토큰이 다르면 409로 거부한다.
- 정보·선택·서류·정책 내용 변경 후 기존 작업은 재확인이 필요하다. 오래된 작업의 완료 처리도 거부한다. 재승인 시 유효 작업은 할 일로 갱신하고 불필요해진 작업은 과거 기록으로 보존한다.
- SQLite 기존 작업에 fingerprint 컬럼을 추가하는 마이그레이션을 검증했다. 작업 ID는 보존하고 최초 재승인을 요구한다.
- 모델이 반환한 도구 이름·인수는 서버가 검증한다. 사실 추출은 제안 단계이며 사용자가 확인해야 저장한다. 모델에 준비 작업 저장·신청 도구는 제공하지 않는다.
- 모델 미연결, 잘못된 인수, 허용되지 않은 도구, 출력 잘림, 시간초과, 호출 횟수 초과를 처리·기록한다.
- 마지막 가상 세션 ID를 브라우저에 보관해 새로고침 후 준비판을 복원한다.

## AI 실연동에서 발견한 실패와 최종 방식

첫 native tools 요청에서 설치된 모델은 도구를 실행하지 않고 설명만 생성했다. 이 결과는 성공으로 계산하지 않았다. 원인을 특정 라이브러리 버그로 확정하지 않는다.

최종 구현은 [Ollama JSON 스키마 출력](https://docs.ollama.com/capabilities/structured-outputs)을 사용한다. 모델이 `calls` 배열에 실행할 도구 이름과 인수를 생성하고, 서버가 허용 목록·타입을 검사해 실제 함수를 실행한 뒤 결과를 모델에 돌려준다. 규칙/키워드로 도구 실행을 흉내 내는 방식이 아니다. native function calling과는 구분해서 설명해야 한다.

실제 모델 검증에 사용한 도구는 `update_user_facts`, `analyze_selected_policies`, `preview_preparation_tasks`다. 자연어 답변에는 오류 가능성이 남으므로 화면의 규칙 판별 결과와 출처가 기준이다. `grounded=true`는 판별 또는 준비 도구를 실행했다는 표시이며 문장별 사실 검증 완료를 의미하지 않는다.

## 재현

프로젝트 폴더에서 실행한다.

```powershell
# 최초 설치 또는 검증 환경 재현
.\.venv\Scripts\python.exe -X utf8 -m pip install -r requirements-lock.txt

# 이미 받은 모델은 재사용된다. Ollama는 숨김 백그라운드로 실행된다.
.\run_ollama.ps1
.\.venv\Scripts\python.exe -X utf8 start.py
```

별도 터미널에서:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m pytest -q
.\.venv\Scripts\python.exe -X utf8 tests/browser_smoke.py
.\.venv\Scripts\python.exe -X utf8 tests/live_agent_smoke.py
.\.venv\Scripts\python.exe -X utf8 tests/live_fact_smoke.py
.\.venv\Scripts\python.exe -X utf8 tests/browser_agent_smoke.py
```

브라우저 테스트는 설치된 Microsoft Edge를 사용한다. live/browser 스크립트는 실행 중인 로컬 서버에 가상 세션과 작업을 생성한다. `pytest`는 임시 DB와 모의 모델 전송을 사용하므로 실제 모델 성공 증거와 구별한다. Windows 샌드박스의 socketpair 제한 때문에 TestClient가 멈춘 사례가 있어, 본 검증은 허용된 일반 실행 환경에서 진행했다.

## 시연 순서

1. `http://127.0.0.1:8000`에서 **청년수당 수급 중** 선택: 가상 월세 정책의 방향성 제외와 근거를 확인한다.
2. **서울 취업준비생** 선택: 신청 검토 가능과 현금 월세 대체서류를 확인한다.
3. AI 입력: “가상 프로필에서 나이는 27세이고 월세는 계좌이체로 냈어. 이 두 정보만 변경 제안하고, 변경된 조건으로 자격 분석과 준비 서류를 도구로 확인해 줘. 아직 저장하지 마.”
4. 실제 도구 실행 표시를 확인하고 **위 정보 제안을 확인하고 저장·재분석**을 누른다. 월세 이체내역으로 준비판이 바뀌는지 확인한다.
5. **이 작업들을 승인하고 DB에 저장**을 누르고 작업 하나를 완료한다. 새로고침해 상태가 유지되는지 확인한다.
6. 월세 납부 방식을 바꾸면 기존 작업이 재확인 상태가 된다. 검수 대기 목록의 공식 정책은 선택할 수 없음을 설명한다.

## 취약점 검토와 보완 · 검수용 정책 초안 (v0.17 · 2026-11-18)

검토 범위는 11/17~18에 추가한 코드(걸러보기, 대화, 신청 계획, 앱 화면)와 그 주변이다. 외부 도구로 한 침투 시험이 아니라 코드 읽기와 측정이다.

- 찾은 것과 조치
  - 보안 헤더가 전혀 없었다 → 모든 응답에 `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, 그리고 `/docs`를 뺀 경로에 CSP(`script-src 'self'`, `frame-ancestors 'none'` 등)를 붙였다. 화면이 서버 데이터를 innerHTML로 그리므로, 이스케이프가 빠지는 실수가 있어도 인라인·외부 스크립트가 실행되지 않게 하는 2차 방어다. 이를 위해 `mobile.html`의 인라인 `onload`를 없앴다.
  - 걸러보기·대화·홈이 요청마다 4,020건을 다시 구조화했다(0.78초, 인증 없이 누구나 호출 가능) → 구조화 결과를 메모리에 두고 수집 내용이 바뀔 때만 다시 만든다(다음 호출 0.04초).
  - 로컬 모델 호출에 동시 제한이 없었다 → 한 번에 한 질문만 받고, 답하는 중이면 429로 거절한다.
  - AI가 꺼지거나 응답이 틀리면 대화가 멈췄다 → 정해 둔 낱말 20개로 찾는 대체 경로를 두고, 응답의 `ai` 값과 화면 문구("AI 없이 정해 둔 낱말로 찾았어요")로 AI가 한 일이 아님을 밝힌다. 유료·외부 AI로 바꾸지 않는다.
  - 화면에서 이스케이프하지 않던 값 3곳(서류 키·이름, 시군구 코드)을 이스케이프했다. 모두 서버 상수라 실제 위험은 낮았다.
- 확인만 하고 그대로 둔 것(공개 배포 전에 정해야 함)
  - 인증이 없다. 수집 실행(`POST /api/integrations/ontong/sync`), 기존 에이전트(`/api/agent/message`), 준비 공간 생성이 누구에게나 열려 있다. 준비 공간은 만들 때마다 DB에 행이 남고 개수 제한이 없다. 로컬 실행(127.0.0.1) 전제다.
  - 준비 공간 식별자는 브라우저 localStorage에 있고 그 값을 아는 사람은 그 공간을 쓸 수 있다. 계정이 아니다.
  - 요청 횟수 제한은 모델 호출의 동시 1건뿐이다.
  - 모델에 보내는 것은 사용자의 말뿐이고 정책 글은 보내지 않는다. 모델 출력은 형식 검증 뒤 검색어·나이·취업 상태로만 쓰고 화면 문장으로 쓰지 않는다. 사용자가 지시문을 넣어도 화면 문장은 바뀌지 않는다(모의 응답 테스트로 확인, 실제 모델에 공격 문장을 넣어 보지는 않았다).
- 검수용 정책 초안: `tools/draft_policy.py`가 수집 정책 하나를 `data/policies/`와 같은 형식의 초안으로 옮겨 `data/policy_drafts/`에 쓴다(서버가 읽지 않는 폴더). ## 화면을 팀 화면 파일 구성에 다시 맞춤 (v0.27 · 2026-11-19)

팀이 준 `청년비서_앱.html`(2026-11-18 17:01)을 로컬에 띄워 지금 앱과 화면별로 견줬다. 틀과 색은 같았고 내용 구성이 달랐다. 사용자 결정: 팀 화면에 없는 덧붙인 기능은 **접어서 유지**, 판정 표현은 **지금 표현 유지**(맞아요 / 확인 필요 / 달라요).

- **내 정보**: 팀 화면의 순서와 입력 방식으로 바꿨다. 출생 연월(→ 오늘 기준 만 나이), 주소(시도·시군구, 도로명 주소는 받지 않음), 전입한 달(→ 거주 기간 구간), 취업 상태(취업 준비 중·재직 중·학생 + 코드표의 나머지), 최종 학력, 소득 구간(중위소득 60·100·150% 이하·그 이상), 가구원 수, 주거 형태, 자격증·시험, 받은 지원 이력. 월 소득 금액·학자금 지원구간·'해당하는 것'은 '더 자세히 입력'에 접어 뒀다.
- **소득 구간 비교**(새 판별): 금액 대신 구간을 고르면 구간 전체가 기준 안일 때 '맞아요', 전체가 밖일 때 '달라요', 걸치면 '확인 필요'. 금액을 넣었으면 금액으로 비교한다.
- **지원 찾기**: 카드를 팀 화면처럼 '지역 · 기간 / 이름 / 지원 내용 한 줄 / 상태'로 바꿨다(지원 내용 한 줄은 수집 글의 첫 줄). 조건별 필터와 이름 검색은 접어 뒀다. 여러 정책을 함께 준비할 때는 상세의 '이 정책 준비하기'로 고른다(챗봇의 '결과 보기' 목록에는 체크박스가 그대로 있다).
- **홈**: '놓치기 전에 살펴봐요'를 팀 화면처럼 정책 한 줄로 바꾸고 비교 건수는 접어 뒀다.

## 확인하지 못했던 것 닫기: 인용 문장 자동 대조, 화면 테스트 확대, 남은 화면 대조 (v0.29 · 2026-11-19)

- **인용 문장 자동 대조**(`tools/verify_supplements.py` → `data/supplement_checks.json`): 보완 기록의 출처 주소 86곳을 다시 열어, 인용 문장이 띄어쓰기를 무시하고 페이지 글에 그대로 있는지 확인했다. 85곳이 열렸고, 항목 199개 중 **174개(87%)는 모든 문장이 그대로 있었다.** 20개는 문장을 찾지 못했고 4개는 일부만 찾았고 1개는 페이지가 열리지 않았다. 찾지 못한 것은 대부분 첨부파일이나 스크립트로 그려지는 페이지에서 온 문장이다. 사람 검수를 대신하지 않는다.
- **확인된 문장만 판단에 쓴다**: 출처에서 문장이 확인된 기록만 나이 규칙, 공식 신청 기간, 신청 계획의 서류 목록에 쓴다. 확인되지 않은 25개는 화면에 '자동 대조 안 됨'으로 표시하고 '확인 필요'로만 작용한다(나이 규칙 46개 중 6개가 여기에 든다). 확인된 기록에는 '출처에서 문장 확인' 표시가 붙는다.

- **검증**: 전체 pytest **354개 통과**. `tools/verify_engine.py` 48,240번 판정 위반 0건. 브라우저 테스트 2종 통과(실제 Ollama). 민지 기준 맞아요 1 · 확인 필요 238 · 달라요 1,174(변화 없음).
- **한계**: 자동 대조는 '문장이 페이지에 있다'까지만 확인한다. 그 문장이 올해 공고의 것인지, 뜻을 맞게 옮겼는지는 사람이 봐야 한다. 페이지가 바뀌면 다시 돌려야 한다. 색·간격을 픽셀 단위로 맞춘 것은 아니다.

## 자격증·시험과 주거를 조건 비교에 사용, 새 화면 파일의 남은 차이 반영 (v0.31 · 2026-11-19)

v0.30까지 내 정보의 **자격증 · 시험**과 **주거 형태**는 저장만 하고 비교에 쓰지 않았다. 새 화면 파일(1119)에서 눌러 보지 않았던 동작도 남아 있었다. 둘을 채웠다.

- **대상 시험(응시료 지원)**: 이름·설명·지원 내용에 '응시료'가 있는 정책(수집 4,020건 중 90건)에 '대상 시험' 조건이 생긴다. 내 시험 이름이 안내 글에 그대로 나오거나, 이름으로 읽은 종류(기사·산업기사·기능사·기능장·기술사 → 국가기술자격, 토익·토플·오픽·HSK 등 → 어학, 한국사)가 글에 대상 시험으로 적혀 있으면 '맞아요', 아니면 '확인 필요'다. **글에 없다고 '달라요'로 보지 않는다.** 토익만 적힌 글을 어학 전체로 넓히지 않는다.
- **주거(무주택 요건)**: 조건·지원 내용·참여 제한 글에 '무주택' 문장이 있는 정책(134건)에 '주거' 조건이 생긴다. 자가라고 입력하면 '달라요'(문장에 우대·가능·구입·생애 최초 같은 말이 함께 있으면 단정하지 않고 '확인 필요'), 월세·전세는 주택 소유 여부를 알 수 없어 '확인 필요', 가족과 거주인데 '부모와 따로 거주' 문장이 있으면 그 문장을 근거로 보여 준다.

## 판별 엔진의 완성 기준과 근거의 위치 (v0.36 · 2026-11-19)

사용자와 정리한 것: 청년비서는 신청 준비를 돕고 공식 홈페이지로 넘기는 서비스다. 실제 정책을 사람이 승인하는 것은 목표가 아니다. 이 기준에서 판별 엔진이 할 일을 다섯 가지로 정하고 전체 자료로 쟀다(`data/COVERAGE.md` 3장, `tools/coverage.py`가 만든다).

| 기준 | 잰 값 |
|---|---|
| 비교할 수 있는 정책 모두에 조건별 판정이 나온다 | 1,448 / 1,448 |
| 모든 조건 줄에 근거 문장과 근거의 위치가 붙는다 | 13,085 / 13,085줄 |
| 자격을 확정하지 않는다고 표시한다 | 1,448 / 1,448 |
| 모든 정책에서 공식 페이지로 넘길 수 있다 | 3,995 / 3,995 (그중 공고·신청 주소까지 있는 정책 3,361건) |
| 코드 칸과 조건 글이 어긋나면 단정하지 않는다 | `verify_engine.py` 55,930번 판정 위반 0건 |

- **근거의 위치**: 조건 줄마다 `where`를 붙였다. 공고의 조항 대신, 그 근거가 온통청년 정책 페이지의 어느 항목(연령, 거주지역, 소득, 취업상태, 사업 신청기간, 참여제한 대상 등 누리집에 보이는 이름)에서 나왔는지를 적는다. 조건 글이나 따로 확인한 공식 페이지를 함께 썼으면 그것도 적는다. 화면의 근거 보기에 '위치' 줄로 나온다(팀 화면의 '위치' 줄에 해당).
- **검증 규칙 추가**: 조건 줄에 위치가 비어 있지 않을 것, 취업·학력이 '제한없음'이어도 조건 글이 내 상태와 반대쪽만 말하면 '맞아요'가 아닐 것(3개 규칙).
- **문서**: 제출 재료(`docs/SUBMISSION_DRAFT.md`)에서 '사람이 승인한 정책만 판정한다'를 '자격을 확정하지 않고 공식 페이지로 넘긴다'로 고치고, 승인 0건을 한계가 아니라 꼭 필요하지 않은 단계로 적었다. `CLAUDE.md`의 원칙에 서비스의 끝을 적었다.
- **검증**: 전체 pytest **373개 통과**(새 테스트 1개). `tools/verify_engine.py` 3,995건 × 프로필 14개 = 55,930번 판정 위반 0건. 브라우저 테스트 2종 통과(근거 보기에 위치가 나오는지 확인 추가, 실제 Ollama).
- **이 기준이 말하지 않는 것**(그대로 남는 한계): API에 적힌 값이 공고 원문과 같은지는 재지 않는다(팀 대조 45건 중 32건 불일치. 그래서 공식 페이지로 넘긴다). 조건 글을 낱말로 읽는 규칙이 모든 표현을 잡는지도 재지 않는다. 위의 100%는 '정한 기준 다섯 가지를 다 채웠다'는 뜻이고 '모든 판정이 공고와 일치한다'는 뜻이 아니다.

## '자료가 바뀌었어요' 안내가 내용이 바뀌었을 때만 나오게 (v0.37 · 2026-11-19)

사용자 질문: 저장한 준비 작업에 '자료가 바뀌었어요. 정책을 다시 골라 계획을 승인해 주세요.'가 왜 나오는가. 원인은 재수집(v0.34)이었다. 준비 작업은 저장할 때 그 정책 수집본의 해시를 함께 저장하는데, 재수집에서 코드 칸 4개가 더해져 모든 정책의 해시가 바뀌었다. 신청기간·조건·서류 같은 내용은 그대로인데도 저장된 작업 전부가 다시 승인하라고 나왔다.

- **고친 것**(`desk_service.py`): 지문을 수집 해시 전체가 아니라 **준비 작업에 영향을 주는 칸**으로 만든다. 키워드, 나중에 더한 코드 칸 4개, 등록·수정 시각은 뺀다. 공식 대조 기록은 수집 해시와 그 메모를 빼고 넣는다.
- **이미 저장된 작업**: 옛 방식의 지문으로 저장된 작업은, 그때의 수집본(`ontong_snapshots`)과 지금 수집본의 내용이 같으면 유효하다고 본다. DB의 값은 고치지 않고 읽을 때 견준다. 공식 대조 기록이 있는 정책의 옛 지문은 되살리지 않는다(그런 정책은 다시 승인해야 한다).
- **지켜지는 것**: 신청기간·조건·서류·링크 같은 내용이 바뀌면 이전처럼 '자료가 바뀌었어요'가 나오고 체크가 막힌다. 내용이 그대로면 다시 승인해도 체크해 둔 상태가 지워지지 않는다.
- **실제 DB로 확인**: 저장된 준비 작업 222개(정책 10개)가 모두 유효로 판정된다(고치기 전에는 모두 '자료가 바뀌었어요').
- **검증**: 전체 pytest **375개 통과**(새 테스트 2개). 기존 테스트 1개는 수집 해시 칸만 바꿔 변경을 흉내 냈던 것이라 실제 내용(신청기간)을 바꾸도록 고쳤다. 브라우저 테스트 2종 통과(실제 Ollama).
- **하지 않은 것**: 사용자의 브라우저 화면에서 문구가 사라진 것을 직접 눌러 보지는 않았다(서버 판정으로 확인).

## Render 배포 준비: 공개 배포 모드, Gemini 선택 연결 (v0.48 · 2026-11-22)

사용자 요청: 팀 저장소 기준으로 render.com에 배포. 로컬 AI(Ollama)를 올릴 수 있는지 보고, 안 되면 Gemini 무료 모델을 붙일 것. 어느 쪽 결과가 나은지도 볼 것.

- **Ollama를 Render에 올릴 수 있는가**: 무료 서버로는 안 된다. Render 문서의 무료 서버는 0.1 CPU · 512MB이고 `qwen3:4b` 모델 파일만 2.5GB다. 유료 서버(메모리 8GB 이상)에 Docker로 올리는 것은 가능하지만 GPU가 없어 느리고 비용이 든다. 해 보지는 않았다.
- **Gemini 선택 연결**(`local_agent.py`의 `structured`): 기본은 그대로 로컬 Ollama다. 환경 변수 `AI_PROVIDER=gemini`를 직접 켠 서버에서만 Gemini를 부른다. **Ollama가 꺼졌다고 Gemini로 넘어가지 않는다.** 챗봇(`desk_finder`)과 정책 도우미(`desk_agent`)가 같은 함수를 쓰고, 모델 출력의 형식 검증은 전과 같다. 키는 주소가 아니라 헤더로 보낸다. 503(혼잡)이면 한 번만 다시 묻는다. 이전 소비자 화면(`/classic`)의 에이전트는 바꾸지 않았다(Ollama만).
- **공개 배포 모드**(`PUBLIC_DEPLOY=1`, `access.py`): 관리 기능을 '서버 PC에서 부른 요청'으로 열지 않고 `ADMIN_TOKEN`으로만 연다. 앞단 서버를 거치면 모든 요청이 같은 주소에서 온 것처럼 보이기 때문이다. 요청 횟수는 `X-Forwarded-For`의 첫 주소로 센다(꾸밀 수 있어 관리 권한에는 쓰지 않는다). `start.py`는 `HOST`·`PORT` 환경 변수를 읽고, 없으면 전처럼 127.0.0.1:8000이다.
- **데이터**: 팀 저장소에 올라온 실행 DB를 그대로 쓴다(따로 채우는 장치는 만들지 않았다). `tools/check_data.py` 어긋남 0건(수집 3,995건, 사라진 37건 포함 4,032행, integrity ok).
- **설정 파일**: 저장소 맨 위 `render.yaml`. 연결 순서와 주의할 점은 `OPERATIONS.md` 3-1.

**Ollama와 Gemini 비교** (`tests/live_finder_eval.py`의 질문 40개와 공격 문장 5개. 2026-11-22 이 PC에서 한 번씩 돌린 값이고 평균 성능이 아니다)

| 응답을 받은 질문 | 39 / 40 (첫 질문에서 500 한 번) | 36 / 40 (503 혼잡 네 번) |

- 정확도는 두 모델이 비슷하다. 받은 응답 안에서는 둘 다 검색어·나이를 모두 맞혔고 취업 상태를 하나씩 놓쳤다(서로 다른 질문).

- Gemini 호출은 연결 시험 2번 + 평가 45번 + 끝까지 돌려 보기 4번 안팎 = 50번 남짓 했다(사용자가 80번까지 허락).

**검증**
- 전체 pytest **395개 통과**(새 테스트 2개: 공개 배포 모드의 관리 기능 잠금과 주소 세기, Gemini는 켰을 때만).
- Render와 같은 조건(`HOST`·`PORT`·`PUBLIC_DEPLOY=1`·`AI_PROVIDER=gemini`, 키 없음, DB는 복사본)으로 서버를 따로 띄워 봤다: 3.9초에 뜨고, 정책 3,995건, `/`·`/desk`·`/review`·화면 파일 200, 토큰 없는 수집 요청과 주소를 127.0.0.1로 꾸민 요청 모두 403, 키가 없을 때 챗봇은 낱말로 찾아 222건.
- 같은 조건에 실제 Gemini 키를 넣어 한 번씩 끝까지 돌렸다: 챗봇("스물여섯 살 취준생인데 서울에서 월세 지원 받을 수 있어?")은 AI가 검색어 '월세'를 골라 222건을 찾았고, 정책 도우미(중랑구 자격증 응시료)는 도구 두 개(`read_policy`, `preview_tasks`)를 부른 뒤 검증된 문구로 답했다.

**하지 않은 것 · 한계**
- **실제 Render 배포는 하지 않았다.** Render 계정 로그인과 저장소 연결은 사람이 해야 한다. 0.1 CPU에서 뜨는 데 걸리는 시간, 512MB 안에 들어가는지는 실제 서버에서 확인하지 못했다(이 PC에서 서버 메모리 최대 138MB).
- 화면(`static/mobile.js`)은 고치지 않았다. Gemini를 쓰는 서버에서도 정책 상세의 'AI에게 물어보기' 카드에 '로컬 AI'라고 나온다. 서버가 만드는 안내 문장은 '로컬'을 뺐다.
- 챗봇은 한 번에 한 질문만 받는 잠금이 그대로다. 여러 사람이 동시에 물으면 "AI가 다른 질문에 답하고 있어요"가 나올 수 있다.

## 대화 오케스트레이터: 팀 문서 'MVP 구조'대로 (v0.48 · 2026-11-22)
- **왜**: 팀 문서 `청년비서_MVP_구조.html`의 구성은 "대화 오케스트레이터(LLM) 1개 + 코드 도구 4개(질문 선택기·판별 엔진·충돌·순서 플래너·서류 준비판)"이다. 챗봇(`desk_finder.py`)은 말 읽기 → 판별 엔진 → 질문 선택기까지만 했고, 부를 도구를 정하거나 플래너로 이어 가지 않았다. 한 턴에 누가 무엇을 했는지도 보이지 않았다.
- **넣은 것**
  - **도구 선택**: 로컬 모델이 말을 읽고 충돌·순서 플래너를 부를지 정한다(`tools`: find는 항상, plan은 '함께·둘 다·중복·순서·합친 금액'을 물을 때). 모델이 놓쳐도 말에 그 낱말이 있으면 코드가 부른다. AI가 꺼져 있어도 같은 길로 간다.
  - **플래너까지 이어 부르기**: 플래너를 부르기로 하면, 내게 해당할 수 있는 위쪽 정책 2~3건을 팀원의 `planner.plan`에 넘긴다(`desk_plan.compare`, 읽기 전용, 준비 공간 불필요). 화면 문장은 플래너가 틀로 만든 `brief`를 그대로 쓴다.
  - **한 턴의 처리 순서**: 응답의 `steps`에 실제로 실행한 것만 적는다(대화 오케스트레이터 → 내 정보 확인 → 판별 엔진 → 충돌·순서 플래너 → 질문 선택기 → 출력 검사). 챗봇 화면에 '함께 보면' 말풍선과 접힌 '이번 답을 만든 순서'로 나온다.
  - 판단은 여전히 코드가 낸다. 모델은 검색어·말에서 읽은 값·도구 선택만 하고 문장을 쓰지 않는다.
- **도중에 고친 것(실제 모델로 드러남)**
  - 도구 선택을 검색어 고르기와 **한 번에** 시켰더니 실제 모델 40문항 평가가 40 → 39로 떨어졌다(예: "강북구 사는 26살 취준생인데 월세 지원 받을 수 있어?"에서 검색어를 '강북구'로 고름). 검색어 프롬프트와 형식은 원래대로 되돌리고, 도구 선택은 **따로 한 번** 묻게 했다.
  - 두 호출의 `num_ctx`가 다르면 Ollama가 호출마다 모델을 다시 올려 한 질문에 10초 넘게 걸렸다. 같은 값으로 맞췄다(질문당 3~4초).
- **하지 않은 것**: 서류 준비판(`docboard`)은 대화에서 부르지 않는다(신청 계획 화면에서만 쓴다). 문서의 '결과 설명을 LLM이 문장으로', '문의 문구 생성', Vercel·Gemini 배포 구성은 넣지 않았다(문장은 틀로 만들고, AI는 로컬 Ollama만 쓴다는 원칙 때문).
- **알려진 한계**: 모델만의 도구 선택은 약하다. 플래너가 필요한 질문 3개 중 모델이 고른 것은 1개("둘 다 받을 수 있어?")였고, 나머지 2개("뭐부터 신청해야 돼?", "중복 돼?")는 코드의 낱말 규칙이 불렀다. 위쪽 2~3건에 같은 사업의 다른 등록 건이 들어가면 금액이 겹쳐 더해진다(실제 확인: 미추홀구·인천시 응시료 지원이 함께 들어가 25만원으로 나옴. 시연 시나리오의 15만원과 다르다).
- **검증**: 전체 pytest **394개 통과**(새 테스트 1개. 팀원 PR #3 병합 뒤 393개 위에). 실제 Ollama `qwen3:4b`로 `tests/live_finder_eval.py` **40/40**(검색어·나이·취업 상태, 공격 문장 5개 형식 안, 중앙값 3.6초·최대 6.5초). 실제 서버에서 질문 5개를 보내 플래너가 필요한 질문에만 `steps`에 플래너가 들어가는 것을 확인. 브라우저 테스트 2종 통과. 따로 띄운 브라우저에서 "응시료 지원이랑 면접 지원 둘 다 받을 수 있어?"를 보내 '함께 보면'과 '이번 답을 만든 순서' 5단계가 나오는 화면을 사진으로 확인(페이지 오류 0건). `tools/verify_engine.py`는 판정 코드를 바꾸지 않아 다시 돌리지 않았다.

- **사람과 함께 받는다는 말**: '아내와 함께 받을 수 있는 신혼부부 지원'은 정책 여러 개를 묻는 말이 아니다. '(가족·친구…)와 함께·같이·둘이'는 빼고 낱말 규칙을 보고, 이때는 모델의 선택도 쓰지 않는다.
- **놓치던 꼴**: 'A 받는데(받는 중인데·받았는데) B도(또) 받을 수 있어?', '두 군데서 받을 수 있어?', '한꺼번에 받을 수 있나', '겹치면 안 돼?'를 낱말 규칙에 넣었다.
- **주제 없이 물으면 아무 3건을 넘기던 것**: 화면에서 이미 고른 정책 번호(`selected`, 5개까지)를 대화 요청에 함께 보내고, '뭐부터 신청해야 돼?'·'준비할 서류 알려줘'처럼 **주제 없이** 물으면 그 정책들로 도구를 부른다. 내 정보가 없어도 고른 정책은 함께 볼 수 있다. 없는 번호는 뺀다.
- **내 지역에 없는 정책은 '찾지 못했어요'로 끝나던 것**: 판별 엔진의 결과를 옮겨 까닭을 적는다. 예: "'청년수당' 정책은 14건 있지만 내게 해당할 수 있는 것이 없어요. 등록된 조건이 내 정보와 다른 정책이 1건이에요(예: 「2026 서울광역청년센터 운영」은 지역 조건이 달라요)."

## 신청기간은 표시만, 판정에서 뺌 (v0.56 · 2026-11-22)
- **왜**: 시연 프로필(26세·인천 미추홀구·미취업)로 보면 비교 가능한 1,403건 중 '맞아요'가 **0건**이었다. '확인 필요' 288건 중 286건에 신청기간이 걸려 있었고, 그중 263건은 '상시로 등록돼 있습니다'였다(사용자 요청: 신청기간은 정책 옆에 표시만 하고 판별에 넣지 않게).
- **바꾼 것**(`screening.screen`): 신청기간 줄은 근거와 함께 그대로 만들되 `counted: False`로 표시하고, 전체 판정(`outcome`)과 확인할 것(`to_confirm`)에서 뺀다(`UNCOUNTED = ('period',)`). 마감된 정책은 전처럼 목록에서 '원문 링크만'으로 나뉘어 판정 건수에 들지 않는다. 화면에서는 상세의 '조건 대조' 목록과 카드의 '맞아요 N · 확인 필요 M' 셈에서 빼고, 기간은 정책 이름 옆 표시(D-day · 상시 · 연중 표기)로만 보여 준다. 챗봇의 못 찾은 까닭에도 기간을 '다른 조건'으로 적지 않는다.
- **결과**(2026-11-22 기준): 인천 미추홀구 민지 — 맞아요 **0 → 40** · 확인 필요 288 → 248 · 달라요 1,115(그대로). 서울 마포 민지 — 맞아요 49 · 확인 필요 197 · 달라요 1,157. 예: '청년 국가기술자격 응시료 지원 사업'이 '조건 맞아요'(나이·거주지·소득·취업 상태·대상 시험).
- **남은 것**: '확인 필요' 248건 중 가장 많은 까닭은 이제 '신청 방법'(온통청년 정보에 신청 방법과 신청 주소가 없음)으로, 그것만 걸린 것이 83건이다. 이것도 내 조건이 아니라 절차라서 같은 방식으로 뺄 수 있지만 요청 범위가 아니라 그대로 두었다.
- **검증**: 전체 pytest **423개 통과**(기간이 판정을 바꾸던 것을 기대하던 테스트 6개를 새 규칙으로 고쳤다: 상시·지난 기간·선착순·1년 가까운 기간·공식 종료 기록 모두 기간 줄은 남고 판정은 바꾸지 않음). `tools/verify_engine.py` 55,930번 판정 위반 0건(판정을 다시 계산할 때 기간 줄을 빼도록 검사를 고치고, 표시만 하는 줄은 기간뿐인지 검사를 더했다). `tools/check_data.py` 어긋남 0건. 브라우저 테스트 2종 통과. 실제 브라우저에서 챗봇 답의 '맞는 정책 1건', 결과 칩 '맞아요 1', 상세의 '조건 대조'에 신청기간 줄이 없고 이름 옆에 '상시'가 표시되는 것을 확인(페이지 오류 0건).
