01

최종 제안과 냉정한 판단

+

제품 이름은 청년비서를 유지하고, 첫 버전은 “취업 준비 청년의 지원사업 신청 준비를 끝내는 AI 에이전트”로 좁힌다.

한 문장 제안: 공식 공고의 자격·서류 조건을 해석하고, 사용자의 준비 상태에 맞춰 지금 해야 할 일을 갱신하는 청년 지원사업 신청 준비 에이전트.

핵심 성과는 지원금 수령이나 선정이 아니라, 공고를 해석하고 필요한 준비 항목을 정확히 파악하는 데 드는 시간과 누락을 줄이는 것이다. 신청과 최종 심사는 공식 기관이 수행한다.

판단 대상판단이유
청년정책 검색·추천만 제공수상 주력으로 부족공식 서비스에도 검색·맞춤 정보·상담이 존재
정책 설명을 생성하는 일반 챗봇차별성 부족범용 AI와의 차이가 불명확하고 사실 오류에 취약
제출 조건과 준비 상태를 연결주력으로 채택무엇을 해야 하는지, 어떤 누락을 막았는지 시연·측정 가능
중앙+서울+경기 전 분야를 동시에 구현이번 제출에서 제외조건 검수·예외 처리·갱신 관리가 병목
응시료 지원 중심의 완성된 흐름우선 구현취업 준비와 직접 연결되고 서류·기준일·예외를 보여주기 적합
여러 정책의 공통 서류 통합조건부 확장동일 사용자가 함께 검토할 수 있는 실제 정책 조합을 먼저 검증해야 함
완전 자동 신청·서류 발급제외인증·권한·외부 시스템 의존성이 크고 준비 지원만으로 핵심 가치 검증 가능

수상 여부는 경쟁팀과 심사에 달려 있다. 지금 단계에서 예상 점수나 수상 확률을 제시할 근거는 없다. 이 계획의 목적은 배점이 큰 항목에 평가 가능한 증거를 쌓는 것이다.

주관기관이 중요하게 볼 것: 공고와 추론의 구분

+

공고에서 확인되는 기준은 청년의 일·생활 문제, AI의 적절한 실사용, 작동하는 결과물, 오류 대응이다. 본선에서 AI 25점과 구현 20점이 가장 큰 묶음이며 동점 우선순위도 이 두 항목부터다. 최종 순위에 예선 점수가 합산되지 않는다. 이는 사용자가 제공한 공고 본문을 근거로 한다.

대한상공회의소를 일반 기업의 매출 과제로 해석할 필요는 없다. 공식 디지털 선도기업 아카데미 취업지원 안내는 훈련생·기업 연결과 직무 역량 지원을 설명한다. 따라서 배운 AI 기술로 실제 문제를 정의하고, 검증 가능한 서비스를 완성했는지를 중시할 것이라는 해석은 공고 및 행사 맥락과 부합한다. 단, 내부 심사위원의 숨은 선호를 확인한 것은 아니다. 대한상공회의소 취업지원 플랫폼 ↗

06

사용자 경험: 채팅과 작업판을 함께 사용

+

첫 화면에는 ‘가상 시나리오로 체험’과 데이터 기준일을 표시한다. 좌측은 질문·답변, 우측은 자격 조건·서류·다음 행동 작업판으로 구성한다. 긴 채팅을 읽어야만 진행 상황을 알 수 있는 구조는 피한다.

  1. 가상 청년 시나리오 선택: 응시 이력·거주 이력·취업 이력이 포함된 합성 데이터.
  2. 목표 선택: 응시료 지원 준비, 가지고 있는 서류 검토, 변경된 모집 확인.
  3. 필요한 조건 확인: ‘현재 일하는가’와 ‘응시일에 일했는가’를 혼동하지 않게 질문.
  4. 후보 표시: 지역·시기·검수 범위로 선별. 불확실한 항목은 숨기지 않음.
  5. 정책 선택: 조건별 판정과 공고 원문 위치 열기.
  6. 서류 상태 확인: 보유 여부만으로 준비 완료 처리하지 않음.
  7. 다음 행동 제시: 원문에 허용된 연동 경로 확인, 발급, 보완, 담당기관 문의 등.
  8. 가상 상태 변경: 새 서류를 준비한 시나리오를 선택하면 영향받는 판단과 행동만 갱신.
  9. 최종 점검: 확인된 항목 수, 남은 필수 항목, 해결하지 못한 조건을 구분.
  10. 공식 신청 창구로 연결: ‘신청 완료’라고 표시하지 않음.

주요 결과 표시는 별도 축을 사용한다.

  • 조건: 충족 / 불충족 / 확인 필요.
  • 접수: 예정 / 기간상 접수 가능 / 종료 / 중단 / 상태 미확인. 예산 잔여 미확인 표시 가능.
  • 서류: 미보유 / 보유·내용 미확인 / 요건 확인 / 재준비 필요 / 공식 창구 연동 확인 필요.
  • 준비: 확인된 준비 항목 n/m, 남은 차단 항목 목록. 이 비율은 선정 확률이 아니다.

예시 문구: “초본이 있다고 답했지만 발급일과 필요한 주소 이력은 아직 확인되지 않았어요.” 날짜 조건은 선택 정책에서 검수한 값만 표시한다. 임의로 ‘3개월 이내’ 같은 조건을 만들지 않는다.

7-1. 수집

  • 첫날 API 접근을 최대 2시간 조사한다. 키 발급·접근이 막히면 수작업으로 검수한 공식 공고를 먼저 적재한다. 런타임을 API에 의존시키지 않는다.

  • policy_id와 round_id를 분리한다. 같은 이름의 다른 연도·시군·모집 차수를 합치지 않는다.

7-5. 갱신과 동결

개발 기간에는 선택 정책의 공식 공고·변경 게시판을 매일 확인한다. 내용 해시가 바뀌면 영향받는 조건만 재추출하되 재검수 전에는 새 버전을 자동 배포하지 않는다. 이후 상용 운영에서는 변경 감지와 검수 큐를 운영 비용의 중심에 둔다.

해커톤 제출 시에는 데이터·프롬프트·모델 설정·규칙·의존성·시연 시나리오를 동결한다. 이후 라이브 재수집으로 평가 데이터를 갱신하지 않는다. 데이터 기준일을 명시하고, 제출 전에 구현한 시간 비교 로직으로 접수 기한 경과를 표시한다. 본선에서 과거 준비 흐름을 재현할 경우 ‘2026-11-22 기준 가상 시나리오’와 실제 현재 상태를 화면에서 명확히 구분한다. 제출 이후 상태 변경을 확인해도 평가 자료를 임의로 수정하지 않고 운영사무국의 규정에 따른다.

08

판단 로직과 서류 통합의 정확한 범위

+

조건 판정은 3값 논리를 사용한다. 필수 AND 조건에서 명확한 불충족이 하나 있으면 불충족, 모두 충족이면 충족, 나머지는 확인 필요다. OR 조건은 하나가 명확히 충족이면 충족, 모두 불충족이면 불충족, 나머지는 확인 필요다. 적용 가능한 예외 조건을 먼저 평가한다. 단순히 모든 조건을 AND로 연결하지 않는다.

단, 위 연산은 필수 조건 목록과 예외의 완결성이 검수된 경우에만 전체 판정에 사용한다. 규칙이 비어 있거나 핵심 항목이 추출되지 않았으면 ‘모두 충족’으로 처리하지 않는다. 접수 상태와 필수 서류 요건이 불명확한 경우에도 ‘신청 준비 완료’를 차단한다. 개별 조건의 충족과 전체 준비 완료는 별도 계산이다.

미확인 사유도 분리한다: 사용자 정보 부족, 원문 누락, 해석 충돌, 접수 상태 미확인, 지원 범위 밖. 각 사유마다 다음 확인 방법과 준비 완료를 막는지 여부를 기록한다.

서류 상태는 정책과 별개로 관리한다. 같은 서류가 A에는 충분하고 B에는 부족할 수 있으므로 document × requirement 단위의 확인 결과를 둔다.

여러 정책의 서류를 통합할 때는 다음 조건을 모두 확인한다.

  • 같은 종류인지: 등본과 초본은 별개.
  • 같은 대상자·증명 대상인지.
  • 발급일 유효 범위가 함께 충족되는지.
  • 주소 이력·세대원 등 필수 기재 항목이 맞는지.
  • 주민번호 노출/가림 조건이 충돌하지 않는지.
  • 온라인 연동·사본·원본 등 허용 제출 방식이 맞는지.
  • 중복 수혜·동일 비용 이중 보전 제한이 없는지.

단순히 더 많은 정보가 들어간 서류가 항상 좋다고 판단하지 않는다. 조건이 상충하거나 불명확하면 분리하고 이유를 표시한다. 공동 준비와 중복 수혜 가능성을 혼동하지 않는다.

다음 행동은 작은 의존 관계로 만든다. ‘정책 선택 → 필수 조건 확인 → 제출 경로 확인 → 서류 요건 점검 → 부족분 준비 → 최종 점검’으로 연결한다. 동일 사용자가 완료한 행동이 다른 요구사항도 충족할 때에만 재사용한다.

AI의 기여는 ‘사용했다’로 끝내지 않는다. 같은 공고를 준 범용 챗봇, 정적 체크리스트, 청년비서를 같은 과업에서 비교한다. 복잡한 예외나 재준비 상황에서도 성능 이득이 없다면 에이전트 구성의 효과를 과장하지 않고 기능을 단순화한다.

개인정보 규칙을 구현에 반영

+

사용자가 제공한 공고는 동의 여부와 관계없이 실제 개인정보·민감정보의 외부 AI 전송을 금지한다. 이를 단순 동의창이나 ‘개인정보를 입력하지 마세요’ 문구로만 처리하지 않는다.

무료 Gemini 이용약관은 제출 내용·응답의 제품 개선 이용과 사람 검토 가능성을 설명하고 개인정보·민감정보·기밀정보를 보내지 말라고 명시한다. 따라서 대회 규칙과 별도로 공개 사용이 허용된 공고에서 불필요한 인적사항을 제거한 텍스트 + 완전 합성 상태만 전송한다. 개발 AI에도 비밀키·실제 인터뷰 원문·참가자 정보를 넣지 않는다. Google 무료 서비스 데이터 이용 조건 ↗

제출 MVP는 공식 정책 사실 + 완전 합성 인물·서류 상태로 체험하도록 한다. 실제 파일 업로드, 실제 이름·생년월일·주소·소득의 자유 입력을 제거한다. 서버는 사전에 생성한 scenarioId, eventId, answerId, actionId만 허용하고 원문 문자열 필드는 거부한다. 모델에 보내는 가상 상태는 서버가 승인된 시나리오 카탈로그에서 구성한다. 숨겨진 API 경로로 실제 텍스트를 보낼 수 없게 테스트한다.

시연에서 선택 가능한 가상 상태 조합은 실제 입력 변화에 따라 규칙과 AI 결과가 바뀌게 만든다. 특정 결과 문장을 클릭마다 고정 출력하는 연출과 구분한다. 가상 시나리오를 쓰는 것은 규정 준수를 위한 선택이며, 실제 이용자의 개인정보를 처리하는 상용 서비스가 이미 완성된 것은 아니다.

사용성 테스트도 참가자 자신의 개인정보 대신 같은 합성 프로필로 수행한다. 인터뷰 원문·개인 이력·화면 녹화 등을 외부 AI에 그대로 넣지 않는다. 실제 서비스 확장은 별도 개인정보 설계·규정 검토·로컬 처리 등의 검증이 필요하며 이번 제출 범위 밖이라고 명시한다.

운영 보안의 최소 범위는 서버 측 API 키, 입력 길이/ID 검증, 호출 횟수 제한, 비밀 값이 없는 로그, 허용된 공식 URL 목록, 외부 문서의 프롬프트 지시 무시다. 외부 문서는 정책 데이터이며 프로그램의 지시사항으로 실행하지 않는다.

Google 공식 문서는 신규 계정의 무료 구간과 일부 프로젝트의 확인 절차를 설명한다. 실제 프로젝트가 무료 상태인지 확인하고, 결제 계정 연결·유료 티어 전환·유료 부가 기능을 하지 않는다. 이를 위해 다른 사람의 API 키를 쓰거나 계정을 여러 개 만들어 한도를 우회하지 않는다. 청구·무료 티어 안내 ↗

호출 예산 설계. Gemini 한도는 프로젝트별 RPM·입력 TPM·RPD 등을 확인해야 하며 API 키를 추가한다고 별도 할당량이 생기지 않는다. RPD 초기화는 태평양 시간 자정 기준이다. 대시보드의 실제 값과 초기화 시각을 기록하고 이에 맞춰 서버의 창을 계산한다. 숫자를 확인하기 전 ‘하루 몇 회 무료’라고 약속하지 않는다. 실제 한도 확인 방법 ↗

개발셋·회귀셋·최종 평가셋은 유지하되, UI·규칙 반복 검증은 테스트용 모델 응답으로 수행해 할당량을 아낀다. 실제 모델 품질·지연·성공률은 라이브 요청만으로 계산한다. 개발 전처리와 사용자 체험이 같은 프로젝트 할당량을 공유할 수 있으므로 함께 관리한다. 별도의 프롬프트를 보내는 개발 AI도 계정의 적용 한도를 확인한다.

심사 접근성. 심사위원에게 개인 API 키 입력이나 로컬 모델 설치를 기본 요구하지 않는다. 무료 프로젝트의 서버 키로 작동하는 공개 URL을 제공하고, 한도가 남아 있어야 한다. D1의 전역 계수·분당 제한·요청 ID 중복 차단과 제한된 시나리오 입력으로 낭비를 줄인다. 공격·서비스 중단까지 완전히 막는다는 보장은 없다. 세션·IP 기반 제한만으로 가용성을 보장한다고 주장하지 않는다.

한도 소진 시 동작: 재시도 가능 시각 안내 → 검수된 준비표 유지 → 이미 생성한 결과는 캐시라고 표시. 사전 검증한 로컬 앱이 있으면 현장 보조 시연에 사용하되 클라우드와 성능 결과를 구분한다. 로컬 앱이나 녹화본만으로 공개 MVP의 실제 AI 가용성 부족이 해소됐다고 보지 않는다. 이 위험이 무료 구성의 가장 큰 한계다.

정책 한 건의 검수 시간·일일 AI 호출 수·실제 토큰 사용량·지연·한도 오류율을 운영 지표로 삼는다. 무료라고 사람이 하는 검수·운영이 사라지지 않는다. 상용 확장 시에도 무료가 유지된다는 가정으로 사업성을 계산하지 않는다.

확장은 청년센터·교육기관 상담 담당자를 첫 파트너 후보로 둔다. 담당자의 반복 설명과 준비 점검을 줄일 수 있다는 도입 가설이며 제휴·구매 의사를 확인한 것은 아니다. 초기에는 이용자 유료 결제보다 상담 도구 활용 실험을 권한다. 지속 수익과 유료 전환율은 미검증이다.

제출 전에 다음 자료를 준비한다. 공식 제출 양식의 필수 구성과 파일 형식·분량 제한은 제공된 양식을 확보한 뒤 맞춘다. 사용자가 붙여준 본문의 제출물 구성 이미지와 별도 ‘AI 활용 및 출처 표기 기준’ 원문까지 확인한 상태는 아니다.

  • 공식 양식의 프로젝트 소개서와 AI 활용 내역.
  • 외부 데이터·모델/API·라이브러리·이미지 출처 및 이용조건 표.
  • 심사위원이 접근·실행 가능한 MVP URL과 실행 안내.
  • 비밀키가 들어 있지 않은 환경변수 예제, 버전 고정 파일, 데이터 버전 기록.
  • 실제 평가 결과와 조건, 합성 시나리오 설명.
  • 제출본으로 촬영한 시연 영상과 네트워크 장애 대응 설명.
  • 제출본 코드·자료·프롬프트·데이터 해시 목록과 백업.
  • 링크 업로드 및 동일 자료 이메일 발송 확인. 이 계획 작성은 메일 발송 권한 부여나 실제 제출을 의미하지 않는다.

출처 이용조건은 사이트 전체를 한 번 확인하는 것으로 끝내지 않는다. 예를 들어 조사한 가평 공고에는 공공누리 제4유형 표기가 있고, 수원 공고에는 출처표시 조건이 안내돼 있다. 개별 첨부·제3자 자료의 권리 범위는 별도 확인이 필요하다. 재사용이 불명확한 원문·이미지는 앱에 그대로 복제하지 말고 허용된 자료를 우선 선택한다. 법적 허용 범위를 이 문서가 확정하는 것은 아니다. 가평 공고 ↗ 수원 공고 ↗

확인되지 않은 주장은 주장 목록에서 보류한다. 특히 다음은 발표 문구에 넣지 않는다: 국내 최초, 유일한 서비스, 신청 성공 보장, 모든 정책 지원, 실시간 완전 갱신, 정확도 100%, 20분 만에 발급 완료, 평균 지원금 증가, 검증되지 않은 제휴·수요·취업 효과.

지금부터의 첫 세 작업

+
  1. 핵심 정책의 최신 상세 공고 묶음 확정: 수원 등 1개 시군을 골라 본문·첨부·정정·FAQ를 확인한다. 조건·서류·기준일·이용조건 중 하나라도 막히면 지역을 바꾼다.
  2. 정답 사례 10개와 준비 화면 1개 작성: AI가 코드부터 쓰기 전에 올바른 출력과 완료 기준을 만든다. 기본 충족·불충족·미확인·기준일 예외·접수 중단을 포함한다.
  3. 하루 안에 배포 가능한 얇은 흐름 구현: 합성 시나리오 → 정책 1개 → 서류 상태 → 다음 행동까지 연결하고, 그 다음 실제 AI를 붙인다. 이후 비교 실험 결과를 보고 확장 여부를 결정한다.

해커톤 공식 URL은 이번 조사 도구에서 본문을 열지 못했으므로 대회 세부 규칙·배점·일정은 사용자가 공유한 공고 본문을 기준으로 삼았다. 공식 해커톤 페이지 ↗에서 제공 양식과 별도 기준을 확보하는 것이 남은 선행 확인이다. 잡아바 신청 화면도 자동 열람이 차단되어 실제 신청 단계와 연동 동작을 직접 검증한 것은 아니다. 따라서 데이터 파이프라인 설계와 후보 선정은 구체화했지만, 실운영 데이터 완결성·모델 접근·사용자 효과는 구현 착수 후 검증해야 한다.
